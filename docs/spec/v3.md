# todo.py v3 – A "done" mező helyett státusz

Állapot: draft. Gazda: @agu5a. A kártyák egy-egy számozott szakaszra hivatkoznak, nem az egész dokumentumra.

## 1. Cél és hatókör

A `done` mező helyett három státusz legyen: `todo`, `in-progress`, `done`. A parancsok és a kimenetek a státuszhoz
igazodnak, és a store fölé kerül egy egyszerű web board, ami a három státuszt oszlopként mutatja.

Minden szakaszra érvényes:

- A program futás közben csak a standard libraryt használja. Fejlesztői függőség (`requirements-dev.txt`, pinelt
  verzióval) csak a §8 böngészős tesztjeihez jön: `playwright`.
- Ami itt nincs megváltoztatva, az marad: parancsok, kimenetek, exit kódok, a `TODO_FILE` környezeti változó.
- Minden új viselkedéshez pytest teszt kell; a meglévő tesztek maradnak. Egy v2-es kimenetet vagy store-t ellenőrző
  teszt csak ott módosítható, ahol ez a spec azt a kimenetet megváltoztatja, és a kártyának meg kell neveznie.
- Parancsonként egy tesztfájl (`tests/test_<parancs>.py`), mint eddig.
- Hiba esetén (nem nulla exit kód) a store fájl nem változik.

## 2. Hibajavítás: hiányos tételek

Ma egy `id` vagy `title` nélküli tétel csendben átmegy: `list` `None [ ] no id` sort ír, `done` `"title": null`-t ment,
`add` `TypeError` tracebackkel áll le.

- Betöltéskor a loader ellenőrzi az összes tételt (ami dict), mielőtt bármelyik parancs dolgozna vele:
  - `id`: `int` (nem `bool`), legalább 1, a fájlon belül egyedi;
  - `title`: nem üres `str`.
- Az első hibás tételnél minden parancs leáll: stderr `Invalid store item <n>: <ok>`, exit 1, a fájl nem változik.
  `<n>` a tétel 1-től számolt sorszáma a fájlban, `<ok>` egy ezek közül: `missing id`, `invalid id`, `duplicate id`,
  `missing title`, `invalid title`.
- A nem dict tételeket a loader továbbra is eldobja (ez a v2 viselkedése, `test_loader_drops_non_dict_items`).
- A többi mező hibás értékére (pl. `priority: "x"`) ez a szakasz nem vonatkozik; `normalize_todo` továbbra sem
  validál.
- Hiányzó store fájl továbbra is üres store.

## 3. Séma v3: státusz

### 3.1 Fájlformátum

```json
{
  "version": 3,
  "todos": [
    {"id": 1, "title": "Pay rent", "status": "in-progress", "priority": "high", "due": "2026-12-01", "labels": ["home"]}
  ]
}
```

A `done` mező helyére a `status` kerül; a mezők sorrendje: `id`, `title`, `status`, `priority`, `due`, `labels`.
`status` egy ezek közül: `todo`, `in-progress`, `done`; alapértelmezés `todo`.

### 3.2 Olvasás és migráció

- v1 (JSON lista) és v2 (`"version": 2`) store v3-ként olvasódik: `done: true` → `"status": "done"`, minden más
  (`false`, hiányzik) → `"status": "todo"`. A `done` mező nem kerül át.
- Minden mentés v3-at ír, mind a hat mezővel. Az első író parancs migrálja a fájlt.
- Csak olvasó parancsok (`list`, `export`, `stats`) soha nem írnak, így nem is migrálnak.
- Bármely más `version` érték: stderr `Unsupported store version: <v>`, exit 1, mint eddig.
- Egy v3 tétel ismeretlen `status` értékkel: §2 szerinti hiba, `<ok>` = `invalid status`.

### 3.3 A meglévő parancsok

| Parancs | v3 viselkedés |
| --- | --- |
| `done <id>` | `status` → `done` |
| `undone <id>` | `status` → `todo` (`in-progress`-ből és `done`-ból is) |
| `clear` | a `done` státuszúakat törli; kimenet változatlan (a törölt darabszám) |
| `list` | jel: `[ ]` todo, `[~]` in-progress, `[x]` done; pl. `3 [~] Write report (high)` |
| `list --open` / `--done` | open = `todo` vagy `in-progress`; done = `done` |
| `list --overdue` | csak nem `done` tételek, mint eddig az open |
| `export --format json` | tételek a hat v3 mezővel |
| `export --format csv` | fejléc `id,title,status,priority,due,labels`; a `status` értéke szövegként |
| `export --format md` | ugyanaz a jel, mint `list`-ben: `- [ ]`, `- [~]`, `- [x]` |

### 3.4 Kód

- Egy helyen (egy függvény) dől el, hogy egy tétel nyitott-e; minden parancs és szűrő ezt hívja.
- Egy helyen van a státusz → jel leképezés; `list` és `export --format md` is ezt használja.
- Az `AGENTS.md` „Data schema” része ugyanebben a változásban frissül.

## 4. `move` parancs és `list --status`

- Új parancs: `move <id> <status>`, a `status` a három érték egyike. Kimenet nincs, exit 0.
  - Ismeretlen id: stderr `Unknown id: <id>`, exit 1.
  - Ismeretlen státusz: argparse hiba, exit 2.
  - Ugyanarra a státuszra mozgatás nem hiba, exit 0.
- `list --status <status>`: csak az adott státuszú tételek. Ismételhető; több megadása „bármelyik” (mint `--priority`).
  Együtt `--open` vagy `--done` flaggel: argparse hiba, exit 2.
- Az `export` ugyanezt a szűrőt kapja (mert a `list` szűrőit veszi át).

## 5. `stats` parancs

Új parancs: `stats`. Csak olvas, kimenete négy sor, mindig ebben a sorrendben:

```text
open: 3
done: 2
overdue: 1
total: 5
```

- `open` és `done` pontosan ugyanazt jelenti, mint `list --open` és `list --done` (ugyanazt a függvényt hívja);
  `overdue` ugyanazt, mint `list --overdue` (`TODO_TODAY` is ugyanúgy hat rá, hibás értéke exit 1).
- Üres vagy hiányzó store: mind a négy érték `0`, exit 0.
- A szakasz nem függ a §3-tól: v2 store-on is működnie kell, és a §3 után is helyes marad, ha a „nyitott-e”
  döntést nem duplikálja.

## 6. Kód szerkezete (refaktor)

A `todo.py` szétbontása csomagra, viselkedésváltozás nélkül.

- Új csomag: `todolib/` (nem `todo/`: a `todo.py` mellett ugyanazon a néven nem lehet csomag).
  - `todolib/store.py`: betöltés, mentés, normalizálás, migráció, `store_path`;
  - `todolib/model.py`: keresés id-re, szűrés, rendezés, a „nyitott-e” döntés, dátum-segédek (`today`);
  - `todolib/render.py`: `list` sorok, utótagok, export formátumok;
  - `todolib/cli.py`: `cmd_*` függvények, `build_parser()`, `main()`.
- A `todo.py` marad a belépési pont (`python todo.py …`), vékony: a `todolib.cli.main()`-t hívja. Amit a tesztek ma
  a `todo` modulból importálnak, az onnan importálható marad (újra-exportálva).
- Parancssori viselkedés, kimenet, exit kód nem változik. Minden meglévő teszt változtatás nélkül zöld; egy teszt
  csak import sort változtathat, és azt a kártya megnevezi.
- Az `AGENTS.md` „Layout” része ugyanebben a változásban frissül.

## 7. Web board

### 7.1 Csak olvasó board

- Új parancs: `serve [--host HOST] [--port PORT]`, alapértelmezés `127.0.0.1` és `8000`. Indításkor stdout
  `Serving on http://<host>:<port>/`, utána Ctrl+C-ig fut, kilépéskor exit 0.
- `http.server` (`ThreadingHTTPServer`), standard library; nincs JavaScript, nincs külső CSS vagy font.
- A szerver létrehozása függvény legyen: `make_server(host, port)` → szerver objektum (`port=0` szabad portot kér),
  hogy a teszt folyamaton belül indíthassa (§8).
- `GET /`: HTML oldal, címe `Board`, három oszlop ebben a sorrendben: `To do`, `In progress`, `Done`
  (mindegyik egy `<section>` `data-status="<status>"` attribútummal). Oszloponként a tételek id szerint,
  tételenként egy `<article data-id="<id>">`, benne `#<id> <title><utótagok>` (ugyanaz az utótag, mint `list`-ben).
  A cím és a címkék HTML-escape-elve (`html.escape`).
- A store-t minden kérésnél újraolvassa (nincs cache), és soha nem írja.
- Hiányzó store: üres board, 200. Store hiba (§2, §3.2): 500, a szövegben ugyanaz az üzenet, mint a CLI stderr-jén.
- Bármely más útvonal: 404.

### 7.2 Mozgatás a boardon

- Minden tétel alatt egy form: `POST /move`, mezők `id` és `status` (egy `<select>` a három értékkel, az aktuális
  kiválasztva) és egy `Move` gomb.
- Sikeres mozgatás után `303 See Other`, `Location: /`. Ugyanaz a szabály, mint a `move` parancsnál (§4), egy helyen
  megírva, a CLI és a web is azt hívja.
- Ismeretlen id: 404, szöveg `Unknown id: <id>`. Hiányzó vagy rossz `id`/`status` mező: 400. Hibánál a store nem változik.

## 8. Tesztek a webhez

- `tests/test_serve.py`: HTTP-szintű tesztek `urllib.request`-tel (böngésző nélkül): oszlopok és tételek a `GET /`
  válaszban, escape-elés, 404, 500 store hibára, `POST /move` 303 és a store tartalma utána, 400 és 404 hibák.
- `tests/ui/test_board_ui.py`: böngészős tesztek a Playwright Python API-jával (chromium, headless), három eset:
  1. a board a három oszlopot és a tételeket a helyes oszlopban mutatja;
  2. egy tétel mozgatása a formmal: az oldal újratöltése után az új oszlopban van, és a store-ban is;
  3. egy `<b>bold</b>` című tétel szövegként jelenik meg, nem formázva.
- Szabály: a szervert a teszt indítja egy pytest fixture-ben (`make_server("127.0.0.1", 0)`, külön szálon,
  `TODO_FILE` a `tmp_path`-ra), és a teszt végén leállítja. Fejlesztő vagy agent ne indítson kézzel háttérszervert.
- A böngészőt a `mise run setup` telepíti (`playwright install chromium`). A böngészős tesztek `ui` pytest markert
  kapnak; a `mise run check` ezeket is futtatja.

## 9. Hibák és exit kódok

| Helyzet | stderr / válasz | exit / HTTP |
| --- | --- | --- |
| Siker | – | 0 / 200 vagy 303 |
| Ismeretlen id | `Unknown id: <id>` | 1 / 404 |
| Nem támogatott store verzió | `Unsupported store version: <v>` | 1 / 500 |
| Hibás tétel (§2, §3.2) | `Invalid store item <n>: <ok>` | 1 / 500 |
| `clear` store fájl nélkül | `No todos file: <path>` | 1 |
| Hibás argumentum (státusz, szint, dátum, címke, flag-kombináció) | argparse usage üzenet | 2 |
| Hibás vagy hiányzó form mező | – | 400 |
| Ismeretlen útvonal | – | 404 |

## 10. Szállítási sorrend

1. §2 először, egyedül: kicsi hibajavítás.
2. Utána §3, §5 és §6 egymástól függetlenek, párhuzamosan mehetnek. Mindhárom ugyanahhoz a kódhoz nyúl (betöltés,
   „nyitott-e” döntés, parancsok), ezért ütközhetnek; aki később merge-öl, rebase után a teljes tesztkészletet futtatja.
3. §4 a §3 után.
4. §7.1 a §3 és a §6 után (a szerver kódja a `todolib/`-be kerül), §7.2 a §7.1 és a §4 után.
5. §8 a §7.2 után; a §7.1 és §7.2 kártyák a saját HTTP-szintű tesztjeiket (`tests/test_serve.py`) maguk hozzák,
   a §8 kártya a böngészős teszteket és a setup-ot.

## 11. Nincs benne

Felhasználók, bejelentkezés, jogosultság; JavaScript, külső CSS vagy font; drag and drop; élő frissítés (websocket,
polling); több store; HTTPS; a szerver elérhetővé tétele a gépen kívülre (a `--host` csak lokális tesztre).
Új státusz hozzáadása, státuszonkénti WIP-limit, a `move` és `undone` közötti „vissza” történet (history).
